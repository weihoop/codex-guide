# Codex 高效使用 10 条

> 说明：本文把常用 Codex 工作流整理成可执行建议。涉及 slash command、Appshots、浏览器标注等能力时，以当前 Codex 版本、官方文档和本机 `codex --help` 为准。

## 1. Prompt 用四段式

不要只说“帮我改”。建议写清楚：

```text
目标：我要实现什么结果。
上下文：相关文件、业务背景、已有问题。
约束：不能改什么、风格要求、安全边界、兼容要求。
完成标准：跑哪些测试、输出什么结果、如何判断完成。
```

示例：

```text
目标：修复登录页移动端按钮溢出。
上下文：React + Tailwind，相关文件在 src/pages/login.tsx。
约束：不改登录逻辑，不引入新依赖，保持现有视觉风格。
完成标准：修改后运行 npm run lint，并说明移动端和桌面端检查点。
```

## 2. 长任务写清楚 goal

长任务不要只给一句“继续优化”。要把“什么叫做完”写成可验证目标。

```text
请持续推进直到满足以下目标：
1. 找出失败测试的根因。
2. 修复问题，不扩大功能范围。
3. 运行相关测试并通过。
4. 总结改动、验证结果和剩余风险。
```

如果当前 Codex 环境支持 `/goal`，可以把这类目标放进 goal；否则直接写在 prompt 中也有效。

## 3. 复杂需求先 plan

多文件、多阶段、风险较高的任务，先让 Codex 读项目结构并输出计划。

```text
请先不要改文件。先阅读相关目录，给出：
1. 你认为需要修改的文件。
2. 每一步改什么。
3. 验证方式。
4. 可能风险。
等我确认后再执行。
```

计划不是越长越好，关键是让方向先对齐。

## 4. 界面问题尽量给截图或 Appshots

前端、桌面端、移动端问题，截图通常比文字描述更准确。

建议附带：

- 当前界面截图。
- 期望效果截图或设计稿。
- 屏幕尺寸或设备类型。
- 你希望保留和改变的部分。

如果当前 Codex 版本支持 Appshots，可用它截取当前窗口，让 Codex 直接读取界面文字和布局。

## 5. 前端样式用可定位描述

不要只说“这里不好看”。建议写成：

```text
在登录页的主按钮：
- 字体小 2px
- 上下 padding 增加 4px
- 移动端宽度占满容器
- hover 颜色保持现有色系，不换主题
```

如果有浏览器标注能力，直接点元素说明改动，比纯文字更准。

## 6. 让 Codex 写测试、跑测试、修测试

交付质量的关键不是“改完”，而是“验证过”。常用提示：

```text
请先补一个能复现问题的测试。
然后修复代码。
如果测试失败，请自己定位原因并继续修，直到相关测试通过。
不要为了通过测试删除有效断言。
```

对于文档项目，也可以用链接检查、敏感词检查、构建检查替代单元测试。

## 7. 项目里必须有 AGENTS.md

`AGENTS.md` 放项目长期规则，不放一次性任务。

建议包含：

- 项目简介和技术栈。
- 常用命令。
- 代码风格和目录约定。
- 测试和验证要求。
- 安全边界和禁止事项。

可以从 `config-templates/AGENTS.template.md` 复制后按项目改写。

## 8. 多模块项目可分层写 AGENTS.md

大型仓库可以在不同目录放不同的 `AGENTS.md`，让规则更贴近模块。

```text
repo/
├── AGENTS.md                 # 全仓库规则
├── frontend/AGENTS.md        # 前端规则
├── backend/AGENTS.md         # 后端规则
└── infra/AGENTS.md           # Terraform/Kubernetes 高风险规则
```

注意：不要让规则互相冲突。更具体目录的规则应只补充本模块需要的内容。

## 9. config.toml 先保守再放开

新项目建议从安全模式开始：

- `sandbox = "workspace-write"`
- `approval = "on-request"`
- 高风险命令需要确认
- 依赖安装、联网、部署、删除操作保留审批

熟悉项目后，再用 execpolicy 放行低风险命令，例如 `rg`、`git status`、`npm run test`。

## 10. 团队衡量“省流程”，不是只看代码行数

Codex 的价值不只是生成代码。更应该看：

- 是否减少重复排查时间。
- 是否自动跑了测试和检查。
- 是否留下了计划、证据和回滚说明。
- 是否让 PR review 更快、更稳。
- 是否降低新人理解项目的成本。

一个好的 Codex 工作流，应该让团队少返工、少漏测、少重复写样板。

## 推荐组合

| 任务 | 推荐用法 |
| --- | --- |
| 小改动 | 四段式 prompt + 相关测试 |
| 多文件改动 | 先 plan，再执行，再验证 |
| 长期任务 | goal + 计划文件 + 阶段性检查 |
| 前端 UI | 截图/Appshots + 可定位样式描述 + 视觉检查 |
| 高风险运维 | read-only 诊断 + 人工确认 + 回滚方案 + 验证 |
| 团队协作 | 项目 AGENTS.md + workflow 文档 + review 检查清单 |
